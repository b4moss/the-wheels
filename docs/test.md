# the-wheels テスト方針

- TDDをベースとする
- 1つのロジック（関数・メソッド）に対し、1つのテストが存在する（単体・結合）
- 1つのロジックに対し
  - 正常系3つぐらい
  - 異常系5つぐらい
  - 以上は目安だが、シンプルな関数だと、この数を必ずしも満たさなくても良い。

## テストの分類

- Vitest
  - 単体テスト -> 単一のロジックに対するテスト
  - 結合テスト -> 複数のロジックがまとまったロジックに対するテスト
- Storybook
  - コンポーネント・カタログと手動の見た目確認に使う
  - 自動ビジュアルリグレッション（VRT）はまだ行わない
  - テストシナリオ（interaction 等）は v0.12.0 で追加
- Playwright
  - E2Eテスト -> 振る舞いがブラウザ上で正しく機能するか -> v0.12.0 でシナリオを追加（それまで本格導入しない）
- スタイル（CSS）
  - 自動テストは行わない
  - 見た目の確認は Storybook 上の手動レビューとする（自動 VRT は未実施）

## カバレッジ

- 開発初期は、速度優先のため、無理にカバレッジを追わない。
- v0.n.0時代は、分岐50%を満たしていれば良い

## TDDの実際ワークフロー

- roadmapごとに、実装する機能の計画を立てる
- 計画に基づき、テスト仕様書を書く
  - `/docs/specs/tests/vX.Y.Z.md`
  - **そのバージョンで実装するロジックをすべて載せる**（1ファイルにその版の対象を集約）
  - 仕様書の書き方は後述
- テスト仕様書を書いてから、POの承認を得る
- 承認後、実装。Red -> Green -> Refactor

### テスト仕様書の書き方

- 1ロジックにつき、テスト可能な単位を見出しにする
  - ピュア関数: 関数シグネチャ（例: `getUserNameFirstLetter(name: string)`）
  - WC / メソッド: クラスとメソッド、または振る舞いの単位名（例: `TwButton#handleClick`、`disable-on-click 属性の反映`）
- その下に、大まかな処理の内容を、自然言語で箇条書きにする
- その下に、テストシナリオを書く（正常系・異常系）
- 異常系は「エラー」だけでなく、期待結果を具体的に書く（例外を投げる / 空文字を返す / 何もしない など）
- ロジックが増える場合は、必要に応じてコンポーネント名などの中見出しでグルーピングしてよい

例:
```markdown
# v0.1.0 テスト仕様

## Avatar

### getUserNameFirstLetter(name: string)

- 引数から名前を取得する
- 最初の1文字を取得する
- 返却する

#### 正常系

- `"山田太郎"` -> `"山"` が返る
- `"12345"` -> `"1"` が返る

#### 異常系

- `null` -> TypeError を投げる
- `""`（空文字） -> `""` を返す
```
